План от 14 октября 2026 года ведётся по `.agent/PLANS.md`. Он продолжает проверенное ядро в `personal-crm/EXECPLAN_CONTINUATION.md`. Изменения CRM остаются внутри `personal-crm/` в ветке `codex/personal-crm-reliability-web`. Создание платных ресурсов, публикация, производственная миграция и остановка Amvera — отдельные действия после подготовки проверяемого результата и предоставления владельцем доступов. ## Purpose / Big Picture

Владелец начинает ежедневно использовать CRM с телефона и компьютера: записывает дело коротким сообщением, видит его в вебе, получает выбранные напоминания и утреннюю сводку. Вход сохраняется после обновления страницы. Приложение работает, когда домашний компьютер выключен. Существующие боты с Amvera затем переносятся на тот же VPS по одному, с сохранением данных и возможностью отката. Другие подходящие проекты получают отдельное окружение на этом сервере; количество проектов ограничивается реальной нагрузкой, а не обещанием «разместить всё без ограничений».

Первый запуск — веб + отдельный Telegram-бот CRM, новые реальные задачи, без почты и платного ИИ. Старые записи переносятся позднее после сверки. Часовой пояс Europe/Moscow, сводка в 09:00, прежние лимиты инициатив максимум две/день и интервал четыре часа. Приоритет интерфейса — быстро записывать дела; сложные формы остаются дополнительной возможностью.

## Context and Orientation

CRM уже реализована на FastAPI/SQLAlchemy/PostgreSQL и React/TypeScript. Есть задачи, заметки, ожидания, поиск, проекты, подтверждения, повторения, шаги, история, постоянная очередь и экспорт. Последняя фактическая проверка: 241 CRM, 133 legacy, 11 React unit, 16 desktop/mobile E2E. Это синтетические испытания, не доказательство работы настоящих Telegram/почты/ИИ или Linux production.

`personal-crm/src/personal_crm/api.py` проверяет owner Bearer credential; `web/src/App.tsx` хранит его только в памяти вкладки, поэтому после перезагрузки нужен новый вход. `/ready` пока возвращает статическое `adapters=fake`, не проверяет свежесть фоновых обработчиков. Worker при выключенном Telegram использует FakeTransport; production не должен с его помощью отмечать настоящие отправки успешными. Source worker и доставка — разные процессы, работающие с общей PostgreSQL. Mail выключен и до отдельного разрешения не включается.

`personal-crm/compose.yaml` содержит изолированные API, источник, очередь и PostgreSQL. Dockerfile использует предварительно подготовленные offline wheels и собранный web/dist; Linux-сборка ещё требует проверки. Существующий корневой Dockerfile запускает `main.py`, старый бот использует polling и SQLite `/data/notes.db`, тренировки `/data/workouts.sqlite3`. Конфигурация репозитория показывает способ запуска, но не текущее содержимое Amvera и не соответствие двух приложений репозиториям. Это соответствие нужно получить из кабинета, не угадывать по названиям GitHub.

VPS — отдельная виртуальная машина с общими процессором, памятью и диском. Docker Compose запускает проекты в отдельных контейнерах — изолированных окружениях с собственными настройками и хранилищами. HTTPS proxy принимает внешний веб-трафик и направляет его нужному приложению. S3 — отдельное объектное хранилище для файлов копий вне VPS.

2026-10-15: владелец не запускал облачную передачу и поручил продолжить здесь. Для фактических Linux испытаний разрешил добавить отдельный `.github/workflows/personal-crm.yml`, остальные изменения остаются внутри personal-crm. Workflow только тестирует, не развёртывает и не читает repository secrets. Изолированный Docker rehearsal должен использовать отдельный project, собственные synthetic env/volumes и локальный CA, с cleanup только собственных ресурсов; настоящие DNS/ACME/S3/Telegram не подключаются.

Выбран общий VPS вместо обязательной покупки отдельного тарифа для каждого нового проекта. При текущих двух ботах за 500 ₽ он дороже уже оплаченной Amvera; выгода — общий ресурс для CRM и следующих небольших приложений. Предпочтительный старт: Beget, 2 vCPU/4 GiB/40 GiB NVMe, Ubuntu 24.04 LTS, публичный IPv4. Это запас для нескольких небольших сервисов, а не измеренное обязательное требование одной CRM. Альтернативные тарифы и увеличение ресурсов не покупать автоматически.

По публичным тарифам на 14 октября сервер 33 ₽/день + IPv4 5 ₽/день дают 1 140–1 178 ₽ за 30–31 день. Отдельное S3 Timeweb 10 GiB опубликовано за 79 ₽/месяц. Базовый ориентир 1 219–1 257 ₽, плановый запас до 1 500 ₽, предельный месячный бюджет владельца 2 000 ₽ без платного ИИ. Перед заказом проверить реальную сумму, выбранный тариф и условия трафика в кабинетах. Новый домен оплачивается отдельно ежегодно; конкретное название согласует владелец перед регистрацией. Эти значения — план, не размещённый заказ. Источники тарифов: https://beget.com/ru/vps и https://timeweb.cloud/services/s3-storage.

Сначала запускать CRM на новых данных в отдельном Telegram-боте. Старые боты сохраняют свои токены, поведение и SQLite при переносе хостинга. Миграция их хостинга и импорт задач в новую CRM — разные операции. Не перехватывать команды тренировок, не включать CRM на токене старого бота и не менять корневой работающий код ради размещения.

Веб-вход: один владелец, пароль, сохранённая защищённая серверная сессия. Открытая регистрация отсутствует. Обновления приложения выкладываются как проверенная версия с возможностью отката; push в GitHub сам по себе не запускает непроверенную версию в production. Публичный репозиторий содержит код и шаблоны, а рабочие ключи/базы находятся на сервере и в защищённых копиях.

## Surprises & Discoveries

При реализации тестовая PostgreSQL оказалась остановленной; запущен только прежний disposable кластер 127.0.0.1:55432. Старый UI mock не знал /auth/session и label «Пароль», обновлён на cookie flow. Desktop capture locator выбирал и название задачи, и кнопку «Открыть»; точное название исправило locator, повтор desktop/mobile прошёл. Новый web auth отзывается при expiry, изменении password hash и восстановлении. Неуспешные пароли commit до возврата 401/429, поэтому counters переживают пересоздание app; per-IP пять, owner aggregate пятьдесят/15min не дают одной IP немедленно заблокировать весь аккаунт.

Первоначально рассматривался отдельный VPS только для CRM. Уточнение владельца расширило цель до общей площадки для проектов и двух действующих Amvera-ботов. Нельзя обосновывать покупку только сравнением памяти CRM: необходимо учитывать суммарную нагрузку и обслуживание сервера. Список доступных GitHub-репозиториев прочитан, но приватные имена не публикуются и содержимое других проектов не исследовалось. Сами репозитории ещё не доказывают, что все проекты пригодны для запуска на одном маленьком сервере.

## Plan of Work

### Этап 1. Удобный и корректный первый ввод

Добавить owner-only сессии в PostgreSQL. Пароль хранится как Argon2id hash, заданный доверенной серверной конфигурацией; пароль/сессионный credential не возвращаются вебу в JSON. Случайный session token в cookie, в БД только SHA-256 token; абсолютный срок 30 дней, logout отзывает текущую сессию, смена пароля отзывает все. Cookie Secure/HttpOnly/SameSite=Strict/Path=/; production имя `__Host-crm_session`. Отдельный явно включённый localhost режим допускает локальные E2E без ослабления production defaults. Изменяющие запросы проверяют Origin и CSRF-token, сохранённый только в памяти веба. Ограничить вход пятью неуспешными попытками за 15 минут на IP и профиль; состояние лимита постоянно хранить в PostgreSQL. Не добавлять Redis или внешний сервис аутентификации.

Добавить `POST /auth/login`, `GET /auth/session`, `POST /auth/logout`. Существующий Bearer оставить для явных технических вызовов; браузер переходит на cookie и CSRF. Доступ recovery_hold остаётся заблокированным. Сессии, попавшие в резервную копию, отзываются при восстановлении; первый вход после восстановления создаёт новую сессию.

Добавить быстрый ввод на экране «Сегодня»: одно текстовое поле и «Записать», Enter отправляет, Shift+Enter переносит строку. `POST /workspace/capture` принимает request_id/text и использует существующие source-first ingest/process, а не независимое хранилище. Ответ возвращает source_version_id и существующий результат create/clarify/proposal/processing/error. При уточнении сразу показать вопрос и поле ответа; retry использует исходный request_id, неоднозначный исход не создаёт вторую задачу. Черновик не теряется при сетевой ошибке. Полная форма остаётся доступна для точных дат, проектов и повторений. Без ИИ интерфейс честно показывает границы поддержанных формулировок.

Ввести явный production режим. При отключённой Telegram-доставке production worker не claim задания и не подменяет её FakeTransport; fake допускается только в явно синтетическом окружении. Аналогично production не использует synthetic mailbox factory. Готовность первого этапа: пароль сохраняет вход после reload, быстрый ввод/уточнение работает на телефоне, сервер не подтверждает fake-отправку.

### Этап 2. Подготовка постоянной работы

Подготовить воспроизводимую Linux-сборку CRM внутри модуля: собрать frontend, создать Linux wheels по lock с проверкой хешей, собрать image и проверить Compose на отдельной синтетической PostgreSQL. Образ фиксируется тегом commit и digest. Тесты/сборки не исполнять на живой пользовательской БД. Добавить запуск контейнеров после перезагрузки, health checks и ограничение размеров технических журналов. За каждым проектом закрепить отдельную Compose-сеть, контейнеры, credentials и постоянные volumes. API/PG не публиковать наружу напрямую; Caddy принимает HTTPS на 443, SSH — по ключу, PostgreSQL доступен только внутренним сервисам.

Добавить постоянные heartbeat записи обработчиков: role/owner/last_seen/status/error_code без личных текстов. Authenticated `GET /workspace/system` показывает реальный статус входа Telegram, доставки, источников, очередь/старейшее ожидание, последнюю успешную внешнюю копию и ошибку. `/ready` возвращает только минимальную готовность, проверяет БД, текущую ревизию схемы, конфигурацию владельца и heartbeat обязательных включённых обработчиков; отключённая почта не считается аварией. Heartbeat каждые 30 секунд, stale после 90 секунд. Внешняя HTTP-проверка каждые пять минут отправляет владельцу уведомление после двух подряд ошибок и одно при восстановлении; конкретный внешний сервис подключить через принадлежащую владельцу учётную запись, не выдавать локальный health check за внешний мониторинг.

Дополнить encrypted backup публикацией в выбранный S3: сначала локальная зашифрованная копия, затем upload, download и проверка AES-GCM/manifest. «Внешняя копия успешна» только после проверенного чтения из S3. Retention 30 дней выполняется после успешной новой remote копии и только для того же database_scope. При сбое upload не удалять последнюю успешную копию. Последний журнал зарегистрированных удалений публикуется отдельно при каждом его изменении; ключ и независимая копия журнала сохраняются владельцем вне VPS. Daily цикл раз в 24 часа, тревога при возрасте успешной копии больше 26 часов. До первого личного ввода восстановить скачанную копию в isolated target; затем повторять rehearsal ежемесячно. Existing restore hold/unknown/неактивные reminders не заменять автоматическим повтором старой очереди.

Провести один нагрузочный прогон: 10 000 синтетических задач, поиск/«Сегодня»/создание, десять параллельных клиентов, очередь и restart. Цель локального API — p95 до 1 секунды для обычных чтений и до 2 секунд для явного сохранения без внешнего провайдера; зафиксировать условия измерения отдельно. Оценить суммарную память/CPU/диск всех планируемых сервисов. Предупреждения: RAM выше 85% в течение десяти минут, диск выше 80%; увеличение тарифа требует отдельного решения. Результат этапа — проверяемый пакет размещения, а не уже оплаченный VPS.

### Этап 3. Первый рабочий запуск CRM

От владельца получить выбранный домен/DNS, SSH-доступ к его VPS, credentials отдельного S3 и нового CRM-бота, подтверждённые Telegram user/chat ID. Секреты вводятся в защищённую серверную конфигурацию, не в репозиторий или публичный документ. Выбранный пример 2/4/40 и итог оплаты показать перед покупкой; аккаунты и платёж остаются у владельца. До предоставления этих данных продолжать локальную разработку/сборку, не ждать их для написания кода.

Развернуть проверенный image на VPS с новой отдельной БД, новым owner и новым паролем; synthetic-web-local и test_web не переносятся. CRM размещается на `crm.<согласованный_домен>`, сертификат автоматически обслуживает Caddy. Зарегистрировать новый бот через BotFather, webhook с отдельным секретом, owner allowlist и проверенным getMe. Включить real ingress/delivery только после успешной проверки HTTPS/владельца/копии. Telegram Update сохраняется до ответа, платный ИИ и почта остаются false. Показать приветствие и короткие примеры поддержанных фраз.

Владелец создаёт пять учебных личных дел, одно точное напоминание через несколько минут, одну регулярную задачу и проект. Проверить вход/сохранение с телефона и компьютера, сообщение → веб → явная правка → фактическое уведомление, повтор Update без дубля, завершение/отмену и сводку 09:00 Москва. На этом этапе уже можно начать ежедневное использование новых задач. Старые Amvera-приложения продолжают работать отдельно.

### Этап 4. Перенос действующих ботов с Amvera

Получить соответствие двух Amvera-приложений GitHub repository/ref, версии image, команды запуска, реальные persistent paths и способ хранения данных. Для известного TG_bot сверять обе SQLite — notes и workouts; второму приложению назначить отдельный runbook после чтения его исходников/конфигурации. Не считать второе приложение копией первого. Репетировать каждый перенос на synthetic данных без настоящего polling/send. Проверить восстановление расписания и поведение просроченных/неопределённых отправок.

На VPS подготовить отдельный проект и volumes для первого бота. В согласованное короткое окно остановить его процесс в Amvera, получить последнюю согласованную копию persistent данных, проверить hash/количества, восстановить на VPS и включить единственный обработчик. Проверить владельца, заметки, будущие reminders, команды тренировок/историю и отсутствие второго получателя Telegram. Не запускать polling двух копий на одном токене. Не делать автоматическую массовую отправку старых событий после простоя. Только после проверки первого бота повторить процедуру для второго.

Оставить прежние Amvera-приложения остановленными, без удаления данных, семь дней после успешного переноса. Откат: остановить VPS-бот, сверить изменения с момента переноса, перенести их назад при наличии новых записей и только потом включить один старый экземпляр. Простое включение старой базы с игнорированием новых записей не является корректным откатом. Amvera ресурсы удалить/закрыть оплату только после подтверждения владельца и сохранения проверенных независимых копий.

### Этап 5. Перенос старых задач в CRM

Этот этап не мешает использовать новую CRM. Получить разрешённую standalone SQLite backup API копию, выполнить existing legacy-preview с выбранным chat и Europe/Moscow, показать количества/архивы/повторы/неперенесённые поля. Импортировать сначала в isolated rehearsal, проверить записи и отсутствие jobs. Подготовить отдельную ограниченную команду production import: require предварительно просмотренный hash, выбранный owner/namespace, backup текущей CRM, тест rollback и явное подтверждение владельца. Не снимать existing guard имен БД без этой команды и проверки.

После подтверждения notes остаются notes, remind_at не становится дедлайном, повторы и старые уведомления не включаются автоматически. Владелец выбирает, какие будущие напоминания/серии включить. Если одинаковые обязательства остаются активными в старом боте и CRM, перед включением нового расписания явно отключить их старую доставку; журнал переноса показывает, что именно выключено. Повтор import не создаёт дубликат, changed row останавливает batch. Тренировки остаются у прежнего бота, не попадают в CRM/ИИ.

### Этап 6. Неделя использования и дальнейшие проекты

В течение семи дней владелец пользуется CRM утром/вечером и отмечает конкретные неудобства: фраза, ожидаемый результат, фактический результат. Личные примеры сохраняются только приватно; в публичные regression tests идут обезличенные/синтетические аналоги. Сначала исправлять потерю/дубли данных, неправильное время, неудобный вход и быстрый ввод; затем ясность «Сегодня», перенос, поиск/проекты. Не добавлять новые интеграции вместо исправления повседневного сценария.

После недели стабильной работы актуализировать матрицу, закрепить релиз и инструкцию из пяти пользовательских действий. Для остальных GitHub-проектов сделать отдельную карту deployable/no-runtime, входных данных, доменов, secrets, диска/памяти и рисков. Статический сайт может обслуживаться Caddy без постоянного Python/Node процесса; тяжёлые приложения, browser automation или локальные модели сначала требуют измерения. Добавлять проекты по одному с лимитами; общие ресурсы не означают общий доступ к базам.

ИИ и почта — следующий opt-in этап после пилота. Для ИИ отдельно выбрать модель/предел расходов/категории передачи, оценить независимый корпус и поведение при timeout/лимите. Для почты отдельно выбрать личный ящик, проверенный readonly способ доступа и папку Sent; сохраняются семь дней, изменения и предложения на подтверждение. До этого реальные флаги остаются выключенными.

## Interfaces and Dependencies

Сохраняются FastAPI, SQLAlchemy, Alembic, PostgreSQL, React и существующие owner/source/task APIs. Новые auth endpoints используют постоянную Session таблицу и отдельную login-rate таблицу, capture переиспользует SourceVersion/Dialogue/Proposal и возвращает существующие discriminated result statuses. WorkerHeartbeat и BackupRun хранят только состояние/время/безопасный код ошибки; `GET /workspace/system` не раскрывает connection strings, адрес S3, секреты и тексты. Установить поддерживаемые проверенные версии Argon2 library, S3 SDK и Caddy, зафиксировать их после Linux compatibility test; новые зависимости не добавлять в корневой бот. Миграции сессий/операционного состояния аддитивные, schema revision в backup формально обновляется вместе с тестом совместимости и откатом. Старые криптоархивы либо явно поддерживаются через отдельный проверенный reader, либо дают понятный unsupported-version до изменения target; не терять их молча при добавлении новой таблицы.

## Validation and Acceptance

До первого личного запуска должны проходить owner login/logout/reload/expiry/revocation, CSRF/Origin/rate-limit, отказ чужому владельцу, быстрый ввод/уточнение/повтор после сети, production disabled delivery без FakeTransport, реальные readiness/heartbeat, startup после reboot, S3 upload failure/remote read/authentication/retention/restore. Миграции аддитивные; восстановление отзывает сессии и не повторяет paid/unknown outcomes. Browser E2E — desktop/mobile.

Первый запуск принят, когда владелец открывает HTTPS CRM с телефона, после reload остаётся вошедшим, записывает понятное дело за одно сообщение, видит его в общей БД, получает назначенное время и сводку 09:00, а ручная отмена предотвращает отправку. После reboot всё работает без ручного запуска Python. Из внешней копии восстанавливаются реальные разрешённые данные в отдельную БД; результаты сверены без отправок. Очередь и возраст копии видны, ошибка не маскируется как «всё проверено».

Перенос бота принят только при сверке его persistent записей/даты/расписания, сохранности тренировок где они есть, одном действующем Telegram-получателе и проверенном откате. Тесты текущего TG_bot не доказывают исправность неизвестного второго приложения. Все новые проекты проходят собственные проверки. Точные даты запуска зависят от окончания этих проверок и предоставления инфраструктурных данных; ориентир планирования — несколько рабочих сессий подготовки, затем семидневный пилот, без гарантии календарного срока до измерений.

## Idempotence and Recovery

Каждый проект получает отдельные директории/volumes, DB credentials и точную версию image. Миграция данных выполняется после backup и сверки, не повторяется слепо после timeout. При неясном исходе прежде проверить фактический commit. Перед rollback остановить новый получатель и учесть записи после переключения. Изменения на VPS не заменяют GitHub commit, а GitHub push не заменяет запуск/проверку.

Первый production deploy и последующие переносы выполняются только с предоставленным владельцем доступом и подтверждённой конкретной процедурой. Этот план не является свидетельством регистрации домена, покупки сервера, разрешения читать произвольную почту или отключения Amvera. Подготовительные code/tests/docs выполнять автономно в разрешённой области.
