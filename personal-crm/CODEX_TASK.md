Это поручение на написание и проверку кода, не запрос на review и не просьба вернуть только план. Пользователь поручил самостоятельно создать рабочую директорию и начать разработку без дополнительных продуктовых вопросов. Каталог документации `personal-crm/` уже создан; самостоятельно создать внутри него структуру исходников, миграций, тестов и локального запуска.

## Контекст и материалы

Рабочий репозиторий: `andreyqwerty365-netizen/TG_bot`.
Подготовленная ветка: `codex/personal-crm-bootstrap`, базовая ветка: `master`.

Сначала прочитать корневой `AGENTS.md`, `.agent/PLANS.md`, `personal-crm/AGENTS.md`, затем полностью `personal-crm/docs/REQUIREMENTS.md`, `personal-crm/docs/OPENAI_API.md`, `personal-crm/docs/ACCEPTANCE.md` и этот документ. Пользовательского чата у следующего агента может не быть; все необходимые требования переданы в этих файлах.

Новый однопользовательский продукт: свободный ввод дел и ручные пересылки Telegram, предложения из почты, сопровождение незаконченных задач, общий веб-обзор. Одна база. Главный риск: потерять обязательство, выдумать срок, изменить существующее дело без разрешения или завалить уведомлениями. Приоритет первой задачи: надёжное ядро, на которое можно безопасно подключать интерфейсы.

Не выполнять merge, force push, deployment, миграцию production или переключение Telegram. Не запускать действующий бот и не использовать найденные токены. Репозиторий публичный: только синтетические примеры, никакой личной переписки или секретов.

Работать на ветке PR. Если среда создаёт собственную ветку, сохранить изменения в отдельной ветке от подготовленного коммита, не в `master`; явно указать это в отчёте. Вернуть проверяемый diff/коммиты в PR, если есть право записи; иначе сохранить доступный патч и честно указать ограничение. Не объявлять код опубликованным без подтверждения.

## Первый завершённый результат

Нужен локально запускаемый сквозной сценарий без настоящих Telegram/OpenAI/почтовых ключей:

Входящая текстовая запись владельца -> надёжная запись источника в PostgreSQL -> тестовая структурированная интерпретация -> серверная проверка полномочий -> создание задачи/предложения -> постоянное задание напоминания -> запуск фонового обработчика -> фиксация попытки доставки через fake-транспорт -> явное закрытие задачи владельцем -> отсутствие устаревшего повтора.

После перезапуска с той же PostgreSQL источник, задача, история и расписание сохраняются. Техническая повторная доставка не создаёт вторую задачу. Письмо создаёт предложение, а не активное дело. Сбой разбора сохраняет источник и не даёт ложного ответа. Этот результат должен демонстрироваться командой и тестами, не описанием будущего поведения.

## M1. Изолированная база приложения

Создать backend Python/FastAPI в отдельном пакете `personal_crm`, свои зависимости и `.gitignore`. Стартовое решение: SQLAlchemy, Alembic, PostgreSQL; версии проверить и зафиксировать. Добавить серверную конфигурацию, явную привязку владельца, проверку доступа, безопасные ошибки, health/readiness и минимальные HTTP-точки для демонстрации сценария. При отсутствующей конфигурации владельца не открывать доступ всем. Аутентифицированный актор определяется сервером, не полем owner_id в запросе. Не делать открытую точку произвольного исполнения model-output.

Миграции минимум для профиля владельца/настроек, источников и их версий, задач/ожиданий, предложений, истории, напоминаний и постоянных заданий/попыток доставки. Проект и дедлайн необязательны. Различать дату и точный момент, исходный и согласованный дедлайн, план выполнения и напоминание; поддержку остальной модели развивать по этапам. Использовать UTC для точных моментов и явный IANA-пояс профиля для календарных вычислений. Не считать тестовый пояс установленным пользовательским поясом.

Создать отдельный Compose `personal-crm/compose.yaml` для PostgreSQL, API и фонового процесса с отдельным volume; реальные отправки отключены. Добавить `.env.example` с пустыми секретами и объяснениями. Не изменять корневую конфигурацию развёртывания.

## M2. Транзакции, полномочия и очередь

Источник фиксируется до внешнего/модельного разбора. Техническая дедупликация по каналу и внешнему идентификатору с корректной областью аккаунта; повторная ручная пересылка не схлопывается по одному тексту. Источник с ошибкой разбора остаётся ожидающим/ошибочным с возможностью повтора, а не теряется. Изменение задачи, журнал и создание/отмена задания фиксируются согласованной транзакцией.

Отдельный сервис политики разрешает явные команды владельца, создание нового очевидного дела из пересылки, предложения из почты. Модель не может повышать уровень доверия источника. Предложения привязаны к версии объекта; не применять устаревшие подтверждения. Закрытие задачи отменяет актуальные связанные будущие отправки, но не стирает журнал.

Очередь на PostgreSQL с захватом задания, сроком владения, восстановлением после остановки, ограниченными попытками и повторной проверкой актуальности перед отправкой. Два обработчика не должны одновременно выполнять одно зарезервированное задание. Исходы доставки: подтверждён, ошибка или неопределённый результат, а не безусловное exactly-once. Сохранить идентификаторы и попытки без полного текста в прикладном логе.

Сделать чистые проверяемые правила уведомлений: одна сводка/день, максимум две инициативы/день профиля, минимум 4 часа между инициативами, точные команды вне лимита, один автоматический повтор через 4 часа с расходованием лимита. Если вся политика не укладывается в текущий запуск, реализовать и проверить безопасный поднабор, остальные строки честно оставить незавершёнными в плане; не объявлять полную поддержку.

## M3. Адаптеры и воспроизводимая демонстрация

Определить интерфейсы интерпретации источника и доставки сообщения. Fake-интерпретатор и fake-отправитель для тестов и демо не делают внешних сетевых вызовов. Тестовые ожидаемые ответы подаются через контролируемые fixtures. Не выдавать небольшой regex или fake за полноценное понимание произвольной русской фразы.

Добавить схему структурированного предложения и проверку неверных дат/запрещённых действий. При отсутствии разрешения, ключа, бюджета настоящий OpenAI не вызывается. По возможности реализовать отключённый по умолчанию адаптер Responses со Structured Outputs, обработкой отказов и серверным бюджетным шлюзом, но рабочее ядро не должно от него зависеть. Оставшиеся реальные интеграции явно обозначить как не подключённые.

Сделать CLI или скрипт демонстрации сквозного сценария на синтетической задаче, который показывает сохранение, рестарт/повторное чтение, отправку в fake-транспорт и закрытие. Отдельная демонстрация: почтовый источник -> предложение -> подтверждение владельцем -> задача. Не подключать реальный Telegram-поллинг ради демо.

## M4. Проверка и передача результата

Добавить unit-тесты и интеграционные тесты на настоящей PostgreSQL. Обязательный минимум: создание без срока; технический дубль; сбой интерпретатора; почта только предложение; запрет недоверенной команды; конфликт версии подтверждения; перенос напоминания без изменения дедлайна; посторонний доступ; перезапуск и очередь; закрытие до отправки; отсутствие внешнего OpenAI-вызова без ключа/бюджета/согласия. Для реализованных правил проверить лимит и единственный повтор с управляемыми часами, без ожидания реальных четырёх часов.

Команды установки/миграций/тестов/демонстрации записать в `personal-crm/README.md`. PostgreSQL можно поднять через Compose либо доступный локальный сервер среды. При отсутствии Docker использовать доступную тестовую PostgreSQL; если она недоступна, честно отметить интеграционные проверки как не выполненные, не заменять доказательство SQLite. Не публиковать выдуманное число успешных тестов.

Проверить, что изменения ограничены `personal-crm/`, секреты отсутствуют, исходный бот не изменён. Обновить `docs/ACCEPTANCE.md` реальными статусами и свидетельствами. Первый результат: работающий код + миграции + тесты + воспроизводимый сценарий + честный список оставшегося. Итоговый ответ на русском.
