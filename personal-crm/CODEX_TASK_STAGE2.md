## Контекст и цель для пользователя

Пользователь хочет писать своему Telegram-боту по-русски одно свободное предложение без обязательных команд, кнопок и форм, например «Завтра в 19:00 напомни обновить резюме», «Надо добавить проект в портфолио», «Перенеси последнее напоминание на субботу», «Выполнил задачу». Он также вручную пересылает сообщения из других чатов. Бот должен сохранить источник, извлечь реальное обязательство, различить своё дело / чужое обещание / заметку / неоднозначность, сохранить задачу и настроить безопасное сопровождение в общем ядре CRM. Ответы короткие на русском после подтверждённого commit. При сложном вводе GPT через OpenAI API опционален, но реальные расходы и передача данных не разрешены автоматически. Основной Telegram-бот продолжает работать независимо до отдельного согласованного переключения.

Не спрашивать пользователя о продуктовом выборе, если можно оставить безопасный изменяемый параметр. Не выдавать fake-сценарий за подключённый Telegram или реально работающую модель.

## M0. Проверка интеграционных границ

Проанализировать текущую Pydantic Interpretation, CRMService.ingest/process/_apply_interpretation/confirm/command, состояние предложений, источник с ревизиями, worker и auth. Зафиксировать реальные изменения схемы, необходимые для обработки пользовательского контекста, подтверждений и Telegram metadata, с безопасными аддитивными миграциями. Выявить сценарий «явная команда владельца с напоминанием»: он должен создавать назначенное точное напоминание без дополнительного подтверждения после проверки полномочий, тогда как предложенное ИИ изменение существующей задачи или перенос по инициативе системы подтверждается. Нельзя передавать модели свободу вызвать произвольный HTTP / DB action.

## M1. Русскоязычные входящие фразы и диалоговые действия

Реализовать расширяемый Interpreter, которому доступны **минимально необходимые проверенные сервером** channel (owner/forward/mail), received_at, original_at (если достоверен), timezone из профиля, сведения о предыдущих предложениях и небольшой набор вероятно относящихся активных задач с ID + version. Модель не должна сама назначать владельца и повышать доверие пересланного текста. Типизировать операции: создание дела, ожидание, заметка, запрос сводки, завершение, перенос reminder/plan/deadline, уточнение, предложение. Ограничить назначение дедлайнов и даты: различать крайнюю дату, день выполнения и время напоминания; при неоднозначности уточнять, не использовать timezone сервера. Относительные даты собственного сообщения считать от даты его получения по явно заданному IANA поясу; относительные даты из старой/неполной пересылки не пересчитывать слепо от сегодняшнего дня. Для «до пятницы», «23 числа», старых forward и DST создать отдельные проверки.

Обрабатывать обычное сообщение владельца без командного префикса, включая «Что на сегодня?», «Последнее выполнил», «Перенеси напоминание на завтра». Однозначная явная команда владельца исполняется сразу. Если подходят несколько задач, спросить уточнение. Связать ответы вроде «да», «нет», «в субботу» с конкретным предложением/уточнением и актуальной версией; диалоговое состояние сохраняется в PostgreSQL, переживает рестарт, истекает по обоснованному сроку и не захватывает несвязанную новую фразу. Изменение существующего дела по инициативе ИИ требует подтверждения. Черновые подшаги не должны самовольно назначать обязательства.

Не пытаться притвориться качественным NLP одним regex. Допустимы ограниченные детерминированные очевидные команды без модели и опциональный адаптер GPT; при выключенной модели неизвестную фразу нужно сохранить и честно попросить уточнение / оставить на разбор, не притворяясь её пониманием.

## M2. Опциональный OpenAI Responses adapter с проверяемой безопасностью

Реализовать серверный adapter через официальный SDK и актуально совместимые Responses API + Structured Outputs со строгой схемой; версия SDK и модель из конфигурации, без hardcode provider pricing в бизнес-логике. Встроить его в существующий pipeline source-first -> interpretation -> server policy -> commit -> ack. Изолировать внешние вызовы от хранения/очереди. Не привязывать существующие напоминания к API. Снизить передаваемый контекст до необходимого, по возможности store=false; не передавать весь inbox, чужие задачи, полные журналы или секреты.

Условия реальных платных вызовов: отдельно включенный флаг, серверный OPENAI_API_KEY, конкретная разрешенная модель и корректная таблица цен, согласие владельца на категории передаваемых данных, положительный месячный бюджет. По умолчанию закрыто. При отсутствии хотя бы одного условия **никаких** сетевых/платных вызовов. Настроить строгий лимит размеров, тайм-ауты и retry только там, где риск и расход контролируются. Для бюджета: транзакционная предварительная резервация консервативной верхней оценки, учёт конкурентных запросов, финальное списание/сверка, предупреждение при 80%, запрет при 100%; если верхняя оценка или цена неизвестны, fail closed. Не объявлять предупреждение достаточной защитой от расхода.

Ошибки сетевого транспорта, невалидные/неполные Structured Outputs, refusal и неверные даты не изменяют задачи молча; источник сохранён, клиент видит корректный статус. Защита от prompt injection: пересланные тексты не могут исполнять вложенные указания об удалении других задач, изменении настроек или раскрытии данных. Промпт модели, а также оценочные примеры, не содержат реальных личных данных. Тесты модели выполняются на mocked SDK/HTTP; реальные OpenAI вызовы не запускать без отдельного разрешения пользователя.

Подготовить синтетический набор не менее 120 размеченных русскоязычных примеров для будущей независимой оценки качества, включая опечатки, относительные даты, отрицания, пересылки, чужие обещания, просьбы без исполнителя, два действия, старые даты, нет обязательства и неясное «это». Не выдавать прохождение mock-тестов за достигнутые метрики качества GPT; при отсутствии разрешения/ключа оценка реального NLP остаётся Not Run.

## M3. Изолированный Telegram Bot API adapter (не переключая рабочий бот)

Внутри personal-crm/ реализовать отдельный адаптер входящих Telegram Updates. Он должен безопасно принимать **synthetic test updates** и иметь отключаемый по умолчанию реальный webhook-маршрут с аутентификацией секретом Telegram webhook (проверка constant-time), явным allowlist Telegram user_id/chat_id и отказом при отсутствующих конфигурациях. Не принимать «owner_id» из payload клиента без серверной аутентификации; не доверять полям from в пересланном контенте вместо фактического автора Update. Чат/идентичность бота должны быть явными server-side настройками. Отвергать неавторизованные сообщения и группы, если они не разрешены. При необходимости поддержать fake-отправку ответов в локальном стенде и реальные исходящие Telegram Bot API сообщения **только после явного enable и с отдельным test-token**, никогда с рабочим токеном существующего бота.

Учитывать Telegram update_id / message_id / edited_message для дедупликации и ревизии, корректно извлекать текст и metadata пересылки (forward_origin или доступный аналог, original date, неизвестный/скрытый автор). Одинаковые тексты, пересланные пользователем разными сообщениями, не схлопывать; технический повтор одного Update не дублирует задачу и ответ. Если источник не содержит текста, не притворяться, что обработаны голос/медиа или вложения. Reply на своё/пересланное сообщение привязать к конкретному источнику, где metadata позволяет; не выдумывать ссылку на личную переписку. Зафиксировать возможность будущей безопасной интеграции с *тем же* существующим ботом через один update consumer; **не запускать второй long polling / webhook в production**.

Исходящая доставка через адаптер должна соблюдать existing worker invariants: bounded network timeouts короче lease, reject if unauthorized/missing token, отчёт о success/error/unknown в зависимости от достоверности результата Telegram API, отсутствие бесконтрольного повтора при неопределённой доставке; безопасный вывод текста без HTML/Markdown инъекций. Входящие короткие подтверждения создания давать только после commit задачи; при сохранении только источника писать правду. Отчёты и debug не содержат полных личных текстов и токенов.

## M4. Тесты, демонстрация, передача

Сценарии, которые должны пройти по локальным synthetic Update и mocked OpenAI, используя настоящую тестовую PostgreSQL:
1. Владелец: «Завтра в 19:00 напомни обновить резюме» -> одна задача и точное напоминание по времени явно настроенного профиля, без ненужного второго подтверждения.
2. «Надо добавить игровой клуб в портфолио» -> задача без придуманного срока, попадает в обзор/ротацию.
3. Пересылка очевидной просьбы -> задача либо вопрос, если получатель/исполнитель неизвестен; источник известен.
4. Пересылка «Я пришлю тебе договор» -> ожидание, не моя задача отправки.
5. Старая пересылка с «завтра» -> запрос уточнения, а не завтрашняя дата относительно пересылки.
6. «Резюме обновил» -> закрытие только одной однозначно найденной задачи; актуальный repeat отменён.
7. «Перенеси напоминание на завтра» -> изменилось reminder, но не исходный дедлайн.
8. «Что на сегодня?» -> обзор по запросу, без расхода лимита инициатив.
9. «Да» к устаревшему предложению -> отказ/уточнение, никаких перезаписей.
10. Технический Telegram Update повторно -> одна операция; новая пересылка того же текста -> отдельный источник.
11. Чужой Telegram user / поддельный webhook secret -> 401/403, никаких данных или отправок.
12. Prompt injection в forwarded / mail не может изменить другие задачи.
13. OpenAI выключен, отказал, timed out, вернул refusal или неверный JSON -> source сохранен, ложного ack нет, фоновая доставка ранее созданных напоминаний продолжает работать.
14. Конкурентные API запросы не обходят бюджет. 80/100% thresholds проверены управляемыми ценами/часами без платных вызовов.
15. Все прежние 69 CRM тестов, 133 теста legacy-бота, 28-дневная симуляция и HTTP/Compose smoke остаются работающими; числа отчёта уточнить по факту.

Тесты и demo не требуют настоящих OPENAI_API_KEY/BOT_TOKEN и не обращаются к Telegram/OpenAI. Проверять конкурентность/очередь только на настоящей тестовой PostgreSQL. Обновить миграции, pinned зависимости, .env.example (пустые placeholder), README с воспроизводимыми командами, матрицу docs/ACCEPTANCE.md и EXECPLAN_STAGE2. При невозможности запустить часть проверки честно указать Not Run, не заменять фиктивным успехом. Не менять рабочий бот и текущую production DB; не коммитить никакие конфиденциальные данные.
