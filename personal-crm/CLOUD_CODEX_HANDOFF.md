### 2. Воспроизведи проверки и исправь обнаруженные проблемы

Пройди CRM tests, legacy tests, React unit, TypeScript/build, browser E2E desktop/mobile, миграции и восстановление. Legacy tests запускай отдельно из корня, явно ограничив каталогом tests, чтобы не смешивать их с набором CRM.

### 3. Доведи production-пакет до проверяемого состояния

Изучи Dockerfile.production, compose.production.yaml и deploy/Caddyfile.

Если Docker доступен, собери runtime и backup images и проверь изолированный Linux-стек на синтетических данных. Зафиксируй точные команды, версии и image digests.

Проверь:
— frontend действительно попадает в image;
— Linux-зависимости устанавливаются из lockfile;
— миграции выполняются до запуска приложения;
— PostgreSQL client совместим с сервером;

## Сохранение результата

Сохраняй проверенные изменения в GitHub доступным облачным механизмом. Продолжай существующую ветку и PR №4, если среда позволяет; не создавай дубликаты PR и не выполняй merge/force push.

Перед публикацией проверь область diff, отсутствие секретов и фактические результаты тестов. Не утверждай «сохранено в GitHub», пока публикация не подтверждена. Если облачная среда требует ручного действия для публикации, подготовь конкретный результат и укажи это действие.

Не останавливайся только потому, что ещё нет SSH или домена: сначала заверши всю доступную подготовку, проверки, исправления и документацию.

## Итоговый отчёт

На русском, кратко:
— что конкретно доведено;
— что и где реально проверено;
— какие проверки не выполнены;
— ссылка на сохранённый commit/PR;
— готов ли пакет к первому VPS-испытанию;
— минимальные данные и действия, которые теперь нужны от меня.

Не объявляй рабочий запуск завершённым до фактического размещения и приёмки.
