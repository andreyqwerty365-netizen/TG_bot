# Почта: чтение, синхронизация и подтверждение

Реальный ящик не подключён. Первый настоящий адаптер реализован для IMAP over TLS и проверен синтетическим транспортом. Доступ к почте пользователя, отправка писем, Telegram и платный ИИ при разработке не использовались.

## Поведение

Первичная загрузка берёт входящие и явно указанную папку отправленных за последние семь суток. Точный фильтр применяется по IMAP INTERNALDATE в UTC, а исходная дата письма сохраняется отдельно. Спам, корзина и черновики не выбираются как папки; флаги Draft/Deleted/Junk исключают письмо из первичной обработки. Адаптер открывает папки через EXAMINE (`readonly=True`), читает UID и `BODY.PEEK`, завершает сеанс LOGOUT. STORE, отправка, удаление, изменение флагов, writable SELECT и CLOSE не используются. TLS проверяет сертификат и имя сервера через `ssl.create_default_context()`.

Права самой серверной учётной записи зависят от провайдера: при будущей настройке использовать минимальные доступные права чтения. Отсутствие команд записи в клиенте не делает обычный пароль технически ограниченным токеном провайдера. Поддерживается TLS IMAP с паролем приложения; OAuth и специфичные HTTP API пока не реализованы. Провайдер и папка отправленных выбираются пользователем, не выводятся из доступных коннекторов чата.

Сверка каждые пять минут читает новые UID после сохранённого номера и по кругу проверяет metadata известных сообщений. Папки чередуются, чтобы большой поток входящих не блокировал отправленные. По умолчанию за проход не больше 25 новых сообщений и 25 проверок известных; тело ограничено 256 KiB, текст — 30 000 символами, цикл сети — примерно 45 секунд плюс ограниченные таймауты завершения. Для oversized письма загружаются только ограниченные заголовки, а полный текст отмечается как недоступный. Вложения не анализируются.

Message-ID обеспечивает идентичность между папками и после повторной загрузки; при его отсутствии используется хэш MIME. Content hash отделяет повтор от новой редакции. References/In-Reply-To связывают цепочку. UIDVALIDITY обнаруживает устаревшую контрольную точку: recent-окно перечитывается, а известные сообщения с Message-ID перепривязываются ограниченными запросами HEADER. Для старого письма без Message-ID безопасно перепривязать UID невозможно; адаптер не приписывает ему другое письмо. Изменение флагов и исчезновение письма обновляют metadata, сохраняют доказательство и не закрывают дело.

Источник, номер редакции и checkpoint фиксируются одной PostgreSQL транзакцией. Разбор выполняется после этого существующим source worker. Сбой разбора не теряет письмо и не требует повторной доставки. PostgreSQL lease запрещает два параллельных прохода; token защищает от запоздавшего результата после отключения/повторного захвата. Сеть и серверные ответы не попадают в прикладные ошибки: сохраняется только категория. После ошибок задержки составляют 5 и 10 минут; третья ошибка останавливает автоматические попытки. Ошибка аутентификации останавливает их сразу. Ручная повторная сверка доступна владельцу; последняя успешная дата не заменяется ложным успехом.

Локальные консервативные правила предлагают задачи из явной просьбы или собственного обещания, ожидание ответа из отправленной просьбы, явную ISO-дату срока и изменение единственного связанного активного дела. Завершение и отмена тоже только предлагаются. Отправка письма сама по себе не доказывает выполнения. Цитируемая старая переписка и подпись не интерпретируются повторно. Это ограниченная грамматика, не понимание произвольной почты: неоднозначные письма показываются для ручного просмотра. Облачный ИИ к этой синхронизации не подключён.

В «Входящих» предложение содержит фрагмент, дату, отправителя, направление и предупреждение о вложениях. HTML преобразуется в текст; браузер выводит его через React escaping, без загрузки ссылок или изображений. Новая редакция делает старое неподтверждённое предложение stale. Подтверждение проверяет владельца и версии; конкурентная правка дела запрещает применение устаревшего предложения. Можно вручную подготовить предложение из неоднозначного письма или отметить его как не требующее дела. Ни один из этих шагов не создаёт активную задачу без «Принять».

Через семь суток полный обработанный кэш очищается: для pending/accepted предложений и связанных дел остаётся фрагмент до 1000 символов; для остальных — отметка очистки без текста/отправителя/темы. Необработанные источники не уничтожаются очисткой. Минимальные hashes/Message-ID/pointer сохраняются для дедупликации. Source worker выполняет очистку даже при отключённом чтении. Это политика основной БД, не процедура удаления из резервных копий.

## Настройка будущего реального подключения

Не включать эти флаги для проверки синтетического стенда. В `.env.example` все секреты пустые, оба разрешения false. Будущий владелец отдельно задаёт `CRM_MAIL_IMAP_HOST`, `CRM_MAIL_IMAP_PORT` (993), `CRM_MAIL_USERNAME`, `CRM_MAIL_PASSWORD`, точное `CRM_MAIL_SENT_FOLDER`, затем явно разрешает `CRM_MAIL_ENABLED=true` и `CRM_MAIL_READ_CONSENT=true`. До обоих разрешений сетевой клиент даже не создаётся. Секреты остаются в серверной среде и не возвращаются вебу. Один профиль поддерживает один ящик; подмена account key останавливается, автоматической смены ящика нет.

После применения миграций к разрешённой среде worker запускается из `personal-crm/`:

    python -m personal_crm.mail_worker
    python -m personal_crm.source_worker

Для Compose добавлен профиль `mail`, использующий ту же конфигурацию API. Он выключен при обычном запуске. Запуск разрешённого настроенного подключения: `docker compose --profile mail up -d crm-mail-worker`. Docker и реальный IMAP в этой итерации не запускались.

Веб показывает состояние в «Настройки → Почта», дату успешной сверки, ошибки, количество сохранённых редакций и восстановлений курсора. «Синхронизировать» не появляется при выключенной серверной интеграции. «Отключить чтение» запрещает дальнейшую запись результата находящегося в сети прохода. Ошибка синхронизации попадает также в обзор и ежедневную сводку.

## Синтетическая демонстрация и проверки

Нужна отдельная PostgreSQL с именем `personal_crm_test*`. Не использовать рабочую БД; pytest пересоздаёт её схему. Из `personal-crm/`, указав тестовый `CRM_TEST_DATABASE_URL`:

    .venv\Scripts\python.exe -m pytest -q

Для воспроизводимой демонстрации указать тот же disposable URL в `CRM_DATABASE_URL`, оставить оба CRM_MAIL-флага false:

    .venv\Scripts\python.exe -m personal_crm.mail_demo
    .venv\Scripts\python.exe -m personal_crm.mail_worker --once

Первая команда сохраняет три синтетических письма, обрабатывает их другим Python-процессом и подтверждает одно предложение. Ожидаемый итог: `saved=3 proposals=2 tasks_before_confirmation=0 tasks_after_confirmation=1 real_external_calls=0`. Вторая выводит `mail worker outcome=disabled` и не подключает ящик.

Браузерный стенд использует другую тестовую БД, например `personal_crm_test_web`, с применённым `alembic upgrade head`. Задать `CRM_OWNER_ID=synthetic-browser-owner`, вымышленный `CRM_OWNER_TOKEN`, `CRM_TIMEZONE=Europe/Moscow`, отключить реальные mail/OpenAI/Telegram-флаги. Затем:

    .venv\Scripts\python.exe -m uvicorn personal_crm.mail_demo:create_demo_app --factory --host 127.0.0.1 --port 8001
    .venv\Scripts\python.exe -m personal_crm.source_worker

Эта специальная фабрика отказывает для иной БД, несинтетического владельца и включённого реального mail. Каждая ручная сверка выдаёт следующую учебную пачку, не обращаясь в сеть. Основная фабрика `personal_crm.api:create_app` не подменяет реальный ящик примерами. Из `web/`:

    npm ci
    npm test
    npm run build
    npm run test:e2e

Для E2E задать `CRM_WEB_TEST_TOKEN`, если credential отличается от документированного вымышленного `synthetic-web-local`, и установить Playwright Chromium. `mail.spec.ts` требует именно синтетическую фабрику и source worker; он проверяет реальную HTTP/PostgreSQL запись, отсутствие задачи до решения, принятие и сохранность после reload на desktop/mobile.

Реализация протокола сверялась с [Python imaplib](https://docs.python.org/3/library/imaplib.html) и [RFC 9051](https://www.rfc-editor.org/rfc/rfc9051.html). Проверки проводятся с синтетическим транспортом: это не доказательство совместимости с конкретным живым провайдером. Для него остаются проверка выбранной аутентификации/папок, read-only прав и квот, согласованный пилот и эксплуатационный мониторинг.
