# Состояние первого VPS и перенос старого бота

15 октября 2026 владелец оплатил FirstVDS: 4 vCPU, 8 GB RAM, 80 GB SSD. Вход по временному отдельному SSH-ключу разрешён владельцем; срок ключа ограничен концом 16 октября по Москве. Установка CRM отдельно от старого бота разрешена пользователем. Адреса, идентификаторы, пароли, ключи и архивы хранятся только в приватном журнале оператора.

На VPS проверены Ubuntu 24.04.5, Docker 29.9.1 / Compose 5.6.0, сборка runtime/backup из commit `4232585`, приватная конфигурация mode 0700/0600, миграции PostgreSQL 16.15, initialize-owner, API и source. Внутренние `/health` и `/ready` вернули alive/ready. Публичный HTTPS с доверенным Let's Encrypt проверен; вход по паролю, Secure/HttpOnly/SameSite cookie и Origin CSRF прошли. После фактической перезагрузки VPS Docker поднял сервисы, `/ready`, сохранённая `/auth/session` и `/tasks` вернули 200. Владелец вошёл в веб. С его отдельного разрешения создана тестовая задача, проверено сохранение после reload, затем задача отмечена выполненной. Реальные почта, ИИ и Telegram выключены.

## Ежедневные внешние копии

Владелец оплатил FirstVDS S3 100 GB за 250 ₽/месяц. Вместе с базовой ценой VPS 1579 ₽ это 1829 ₽/месяц после вводной скидки. Создан отдельный приватный bucket с жёстким лимитом размера 10 GB. Включены backup worker и ежедневный цикл существующего планировщика, 30-дневное хранение и шифрование AES-256-GCM до отправки. Ключ восстановления отдельно сохранён владельцу вне VPS; временную локальную копию нужно перенести в менеджер паролей.

Первый фактический цикл получил `verified_remote`: upload и readback с проверкой расшифровки прошли. Затем архив и журнал удалений скачаны из S3 в пустой отдельный каталог (`downloaded_verified`), восстановлены в отдельную пустую PostgreSQL (`restored_on_hold`, counts совпали). В восстановленной базе все сессии отозваны и включён recovery hold; рабочая `/ready` после проверки вернула 200. UI показывает время проверенной копии и ноль операционных ошибок. Следующий запуск вернул `not_due`, поэтому повторный архив раньше срока не создан. Перезагрузка VPS проверена до включения S3; для backup контейнера проверены restart policy и работа после запуска, отдельный reboot с ним не повторялся.

Credentials получены из приватной панели и записаны только в `/etc/personal-crm/config/backup.env` mode 0600; одноразовые транспортные ключ и зашифрованный конверт на VPS удалены. Серверный storage-user имеет доступ к выделенному S3-хранилищу. IAM-ограничение credentials одним prefix не подтверждено панелью: прикладной scope и отдельный bucket не являются доказательством такого запрета. Не размещать здесь чужие проекты без отдельной проверки полномочий. Независимый uptime monitor и регулярная репетиция восстановления ещё не настроены.

При проверке публичного DNS обнаружен registry status `client hold`, хотя панель посредника показывала DELEGATED. Владелец подтвердил почту; повторный RDAP показал отсутствие hold. После обновления DNS Google и Cloudflare вернули A нового VPS, затем Caddy получил публичный сертификат. Не менять NS и не удалять существующие записи сайта для устранения такой блокировки. После снятия hold дождаться корректного A-ответа, затем запускать Caddy и проверять доверенный публичный сертификат. Статус панели DNS сам по себе не доказывает делегацию из родительской зоны.

Секреты нельзя печатать через `docker compose config`, `env`, shell tracing или журналы. Для проверки использовать `config --quiet`. При выполнении многострочного сценария через SSH stdin одноразовые `docker compose run` запускать с `-T --interactive=false` и `</dev/null`, иначе контейнер может прочитать последующие команды сценария как свой ввод. Для генератора приватной конфигурации с собственным heredoc stdin нужен только этому отдельному запуску.

## Подготовка переноса

Владелец уточнил: переносится один существующий бот, второго нет. Сайт остаётся отдельным приложением. На момент проверки в Amvera приложение бота в новом регионе остановлено; для прежнего Москва_0 провайдер предлагает архивы кода, `/data` и отдельно переменные. Не считать эти архивы свежей согласованной копией только потому, что ссылка на скачивание создана сегодня.

Архивы кода и данных бота скачаны приватно. Для notes.db и workouts.sqlite3 получен SQLite `integrity_check=ok`, WAL/SHM в архиве не обнаружены. Даты файлов старше дня переноса. Не обещать отсутствие утраченных последних записей: нужен выбор владельца или более свежая копия. Базы тренировок и старые копии сохраняются отдельно от PostgreSQL CRM. Импорт данных старого бота в CRM не выполняется.

Архивный commit определён приватно; в локальных Git objects его нет. Сравнение 44 runtime файлов с текущим `4232585` выявило восемь изменённых файлов и один отсутствующий в архиве, включая обработчики и зависимости. Текущий HEAD не является подтверждённой копией старого приложения. Образ старого бота пока не собран. Перед переключением выбрать проверенный исходник и сверить зависимости, переменные и persistent paths. Не выполнять файлы из архива и не отправлять его в публичный GitHub. Архив может содержать секреты и историю Git. Создать чистый build context из выбранного проверенного commit, отдельно убедиться, что в нём нет env, баз, архивов и журналов. Собрать старый Dockerfile, записать фактический image ID. Runtime использует UID/GID 10001 и файлы `/data/notes.db`, `/data/workouts.sqlite3`, логи `/data/logs`, исходный `/app/exercises.json`.

Подготовленный `deploy/compose.legacy.yaml` является отдельным проектом, без опубликованных портов. По умолчанию профиль migration не запускается. Дополнительно запуск отказывает без явного `LEGACY_CUTOVER_CONFIRMED=true`, токена и обеих существующих баз; он не создаёт незаметно пустую новую базу. Сам шаблон не доказывает выключение старого Telegram receiver — это отдельная проверка оператора.

На VPS Compose проверен с отдельными синтетическими каталогами и network_mode none: `config --quiet` прошёл, четыре попытки запуска без cutover flag, токена, allowlist или файлов БД отказали с соответствующими безопасными кодами. Настоящий токен и базы старого бота в эти проверки не передавались, polling не запускался.

Создать приватные каталоги конфигурации и данных вне checkout. Скопировать `deploy/examples/legacy.env.example` в `bot.env` mode 0600, заполнить исходные значения приватно. Сохранить прежний allowlist; не заменять его пустым значением и не определять владельца по первому посетителю. Параметры `LEGACY_IMAGE`, `LEGACY_CONFIG_DIRECTORY`, `LEGACY_DATA_DIRECTORY` задаются оператором явно. Каталог данных и логи должны быть доступны UID 10001; исходные backup archives остаются неизменными.

Проверка без запуска получателей:

    docker compose -f deploy/compose.legacy.yaml --profile migration config --quiet

Для реального переключения согласовать короткое окно и проверить, что старый процесс остановлен и Telegram webhook/другой poller не остаётся активным. Сделать последнюю согласованную SQLite backup API копию либо подтвердить выбранную архивную точку восстановления. Записать hashes/counts отдельно для заметок, напоминаний и тренировок. Подготовить откат до первого старта. Только после этого приватно включить флаг и запустить профиль migration.

После старта проверить единственный приёмник, команды заметок/напоминаний и тренировок, пользовательские настройки, расписание, журнал ошибок и состояние healthcheck. Устаревшие напоминания могут отправиться сразу после запуска: их список и желаемое поведение нужно согласовать до запуска. Не включать второй экземпляр для проверки. При откате сначала остановить новый процесс, затем возвращать один старый; сохранить изменения, созданные после переключения.

Внешняя зашифрованная копия CRM не заменяет отдельное резервирование SQLite старого бота. Не закрывать Amvera и не удалять архивы до проверки сохранности данных и восстановления.
