# Состояние первого VPS и перенос старого бота

15 октября 2026 владелец оплатил FirstVDS: 4 vCPU, 8 GB RAM, 80 GB SSD. Вход по временному отдельному SSH-ключу разрешён владельцем; срок ключа ограничен концом 16 октября по Москве. Установка CRM отдельно от старого бота разрешена пользователем. Адреса, идентификаторы, пароли, ключи и архивы хранятся только в приватном журнале оператора.

На VPS проверены Ubuntu 24.04.5, Docker 29.9.1 / Compose 5.6.0, сборка runtime/backup из commit `4232585`, приватная конфигурация mode 0700/0600, миграции PostgreSQL 16.15, initialize-owner, API и source. Внутренние `/health` и `/ready` вернули alive/ready. Публичный HTTPS с доверенным Let's Encrypt проверен; вход по паролю, Secure/HttpOnly/SameSite cookie и Origin CSRF прошли. После фактической перезагрузки VPS Docker поднял сервисы, `/ready`, сохранённая `/auth/session` и `/tasks` вернули 200. Владелец вошёл в веб. С его отдельного разрешения создана тестовая задача, проверено сохранение после reload, затем задача отмечена выполненной. Реальные почта, ИИ и Telegram выключены.

## Ежедневные внешние копии

Владелец оплатил FirstVDS S3 100 GB за 250 ₽/месяц. Вместе с базовой ценой VPS 1579 ₽ это 1829 ₽/месяц после вводной скидки; отдельно согласованный позднее IPv6 добавляет 20 ₽, текущий общий итог — 1849 ₽/месяц. Создан отдельный приватный bucket с жёстким лимитом размера 10 GB. Включены backup worker и ежедневный цикл существующего планировщика, 30-дневное хранение и шифрование AES-256-GCM до отправки. Ключ восстановления отдельно сохранён владельцу вне VPS; временную локальную копию нужно перенести в менеджер паролей.

Первый фактический цикл получил `verified_remote`: upload и readback с проверкой расшифровки прошли. Затем архив и журнал удалений скачаны из S3 в пустой отдельный каталог (`downloaded_verified`), восстановлены в отдельную пустую PostgreSQL (`restored_on_hold`, counts совпали). В восстановленной базе все сессии отозваны и включён recovery hold; рабочая `/ready` после проверки вернула 200. UI показывает время проверенной копии и ноль операционных ошибок. Следующий запуск вернул `not_due`, поэтому повторный архив раньше срока не создан. Перезагрузка VPS проверена до включения S3; для backup контейнера проверены restart policy и работа после запуска, отдельный reboot с ним не повторялся.

Credentials получены из приватной панели и записаны только в `/etc/personal-crm/config/backup.env` mode 0600; одноразовые транспортные ключ и зашифрованный конверт на VPS удалены. Серверный storage-user имеет доступ к выделенному S3-хранилищу. IAM-ограничение credentials одним prefix не подтверждено панелью: прикладной scope и отдельный bucket не являются доказательством такого запрета. Не размещать здесь чужие проекты без отдельной проверки полномочий. Независимый uptime monitor и регулярная репетиция восстановления ещё не настроены.

При проверке публичного DNS обнаружен registry status `client hold`, хотя панель посредника показывала DELEGATED. Владелец подтвердил почту; повторный RDAP показал отсутствие hold. После обновления DNS Google и Cloudflare вернули A нового VPS, затем Caddy получил публичный сертификат. Не менять NS и не удалять существующие записи сайта для устранения такой блокировки. После снятия hold дождаться корректного A-ответа, затем запускать Caddy и проверять доверенный публичный сертификат. Статус панели DNS сам по себе не доказывает делегацию из родительской зоны.

Секреты нельзя печатать через `docker compose config`, `env`, shell tracing или журналы. Для проверки использовать `config --quiet`. При выполнении многострочного сценария через SSH stdin одноразовые `docker compose run` запускать с `-T --interactive=false` и `</dev/null`, иначе контейнер может прочитать последующие команды сценария как свой ввод. Для генератора приватной конфигурации с собственным heredoc stdin нужен только этому отдельному запуску.

## Подготовка переноса

Владелец уточнил: переносится один существующий бот, второго нет. Сайт остаётся отдельным приложением. На момент проверки в Amvera приложение бота в новом регионе остановлено; для прежнего Москва_0 провайдер предлагает архивы кода, `/data` и отдельно переменные. Не считать эти архивы свежей согласованной копией только потому, что ссылка на скачивание создана сегодня.

Архивы кода и данных бота скачаны приватно. Для notes.db и workouts.sqlite3 получен SQLite `integrity_check=ok`, WAL/SHM в архиве не обнаружены. Даты файлов старше дня переноса; 15 октября владелец подтвердил, что более поздних записей не добавлял и эти копии подходят. Базы тренировок и старые копии сохраняются отдельно от PostgreSQL CRM. Импорт данных старого бота в CRM не выполняется.

Архивный commit определён приватно; в локальных Git objects его нет. Сравнение 44 runtime файлов с текущим `4232585` выявило восемь изменённых файлов и один отсутствующий в архиве, включая обработчики и зависимости. Текущий HEAD не является подтверждённой копией старого приложения. Выбран архивный runtime без новых функций текущего HEAD. После статического осмотра создан чистый build context из 56 runtime файлов: только main.py, Dockerfile, requirements-runtime.txt, exercises.json, Python-модули bot/, assets с изображениями и tools/healthcheck.py. Git, env, базы, журналы и исходный архив в build context не включены. Проверены синтаксис Python, шаблоны секретов и hashes файлов; на VPS собран изолированный образ. Архив не публиковать и не использовать его корень напрямую как build context. Runtime использует UID/GID 10001 и файлы `/data/notes.db`, `/data/workouts.sqlite3`, логи `/data/logs`, исходный `/app/exercises.json`.

### Проверенный пакет старого бота

Архивные regression tests выявили два дефекта: создание приложения не отказывало без owner allowlist, а проверка пользователя при пустом allowlist разрешала всех. В `deploy/legacy-owner-allowlist.patch` сохранено минимальное исправление этих двух условий; действующий корневой bot/ не изменён. Сначала два теста упали на исходном архивном коде. После patch они и остальные выбранные проверки прошли на Linux без сети. Два дополнительных первоначальных отказа были вызваны отсутствием requirements.txt и .env.example в тестовом mount; эти архивные файлы предоставлены только тестам, в runtime image они не добавлялись.

`deploy/legacy-runtime.lock` фиксирует все фактически разрешённые runtime dependencies отдельного бота; он не заменяет зависимости CRM или корневого проекта. В чистом runtime context сначала применить patch, проверив совпадение контекста, затем заменить requirements-runtime.txt этим lockfile. Не применять patch к текущему корневому коду или поверх неизвестной версии. Пример из отдельного чистого каталога исходников, где `crm_module` — абсолютный путь к personal-crm:

    git apply --check "$crm_module/deploy/legacy-owner-allowlist.patch"
    git apply "$crm_module/deploy/legacy-owner-allowlist.patch"
    cp "$crm_module/deploy/legacy-runtime.lock" requirements-runtime.txt
    docker build -t legacy-reminder:prepared .
    docker image inspect legacy-reminder:prepared --format '{{.Id}}'

Окончательная сборка с зафиксированными dependencies прошла 151 тест в 16 архивных test modules: SQLite, parser, handlers, owner access, reminders, повторения, экспорт и тренировки. Три test modules для Windows launchers, внешних alert tools и deploy scripts не запускались: они не относятся к этому минимальному Linux runtime context. Проверки выполнялись в отдельном test image с pytest/trio, network none, read-only rootfs, без capabilities и настоящего BOT_TOKEN. pytest и тестовые базы не входят в рабочий image. Подготовленный runtime пока не запущен как Telegram receiver; его фактический image ID записан приватно. `pip check` завершился без конфликтов.

На отдельных локальных копиях обеих выбранных баз выполнены init архивных Database и TrainerDatabase. `integrity_check=ok`; сравнение количества и хешей всех прикладных строк до/после подтвердило сохранность заметок, напоминаний, расписаний, тренировок, подходов и настроек. Оригиналы не изменились. Первоначальное сравнение внутренних FTS shadow tables не совпало из-за штатного rebuild поискового индекса; прикладные строки и виртуальные FTS records совпали. Исторические trainer migrations уже отмечены применёнными.

После отдельного разрешения владельца выбранные базы перенесены на VPS. Репетиция в окончательном Linux runtime без сети прошла: сборка Application с синтетическим токеном, подтверждённым владельцем и реальными копиями, integrity обеих баз и совпадение хешей всех прикладных строк. Проверены отказ чужому ID и отсутствие изменений исходных копий. Через SQLite backup API создана отдельная копия для отката; восстановление проверено integrity и сравнением SQL dumps. Исходные архивы остаются также вне VPS.

Владелец разрешил перенос действующего BOT_TOKEN и включение единственного экземпляра после проверок, а также отправку просроченного напоминания. В архивных env отсутствовал allowlist: после отдельного подтверждения выбран единственный пользователь из базы тренировок. Токен перенесён через одноразовый RSA-OAEP/AES-GCM конверт в приватный bot.env mode 0600, транспортные файлы удалены. Конфигурация и данные вне checkout, data/logs принадлежат UID 10001. После успешных сетевых проверок LEGACY_CUTOVER_CONFIRMED атомарно включён, запущен один receiver.

### Сетевая диагностика и запуск через IPv6

До подключения IPv6 15 октября с хоста VPS и из контейнера не устанавливалось соединение с api.telegram.org:443. Независимые DNS Google/Cloudflare возвращали одинаковый A; HTTPS к S3 работал, UFW разрешал outgoing. tcpdump показал выходящие SYN без ответов, traceroute — только несколько промежуточных узлов. Это доказывает отсутствие ответа на TCP, но не конкретного виновника фильтрации/маршрутизации. Токен не являлся доказанной причиной ошибки. На компьютере владельца тот же IPv4 тоже не отвечал; глобальный сбой Telegram из этого не следует.

С отдельного разрешения владельца в FirstVDS зарегистрирован запрос по этой конкретной сетевой ошибке; номер, адрес VPS и текст остаются в приватном журнале, без токенов и баз. Владелец подтвердил email аккаунта FirstVDS; ограничивающее предупреждение исчезло. На момент самостоятельного решения ответа поддержки не было. Провайдер и базовый тариф не менялись.

Владелец отдельно разрешил подключение IPv6 за 20 ₽/месяц и применение с перезагрузкой. Первый дозаказ составил 0.65 ₽ с баланса, далее ежедневное списание в пределах 20 ₽ за месяц. Общая регулярная стоимость VPS/S3/IPv6 — 1849 ₽/месяц. IPv6 появился на работающем VPS, прежний uptime сохранился, CRM оставалась ready 200. Адрес и gateway присутствуют в постоянном /etc/network/interfaces. Фактическая перезагрузка с новой IPv6-сетью пока не проверялась; не выдавать разрешение на неё за результат теста.

Хост по IPv6 получил HTTPS 302 от api.telegram.org и 200 от core.telegram.org с обычной доверенной TLS-проверкой. Старый Docker bridge после этого всё ещё давал ConnectError: у контейнера не было IPv6-маршрута. В deploy/compose.legacy.yaml добавлен opt-in LEGACY_ENABLE_IPV6, по умолчанию false. Он задаётся в приватном Compose deploy.env, отдельно от bot.env; пример — deploy/examples/legacy-deploy.env.example. На этом VPS значение true. Docker создаёт отдельную dual-stack сеть проекта и автоматически выделяет приватную ULA-подсеть; IP сервера в Git не записан. Глобальный Docker daemon, CRM networks и опубликованные порты не менялись. Механизм динамической IPv6 allocation описан в [официальной документации Docker](https://docs.docker.com/engine/daemon/ipv6/).

Оба режима Compose config --quiet прошли. В новой сети HTTPS API, реальные getMe/getWebhookInfo прошли, webhook отсутствовал, pending updates равнялись нулю. В Amvera повторно проверен остановленный экземпляр. После этого запущен единственный receiver от UID 10001: Application started, healthy, restart count 0, без Conflict/NetworkError/traceback на проверенном интервале. Разрешённое просроченное напоминание отправлено: scheduler сообщил успех reminder job, активный message ID владельца изменился после успешного send_message. Число заметок и напоминаний сохранено, integrity обеих рабочих SQLite ok. Контейнерный healthcheck читает SQLite и может стать healthy раньше готовности Telegram; polling проверять отдельно по фактическому старту приложения и отсутствию конфликтов.

Для дальнейшего старта использовать проверенный image ID и приватный deploy.env с LEGACY_ENABLE_IPV6=true, один профиль migration. При ошибке остановить receiver, сохранить обновлённые базы и оставить флаг false; не перезапускать Amvera автоматически. Для новых данных бота нужен отдельный план внешнего резервирования до удаления Amvera; существующий PostgreSQL backup CRM не копирует эти SQLite. Старый бот сохраняет своё прежнее поведение напоминаний, включая повторы до действия владельца; импорт в CRM не выполнялся.

До включения проверить просроченные напоминания: архивный schedule_reminder запускает их сразу. Согласовать сохранение такого поведения или отдельное действие владельца. Не менять даты и статусы незаметно. Не переносить BOT_SEED_NOTES_B64/BOT_SEED_WORKOUTS_B64 в новый env: они могут перезаписать существующие базы при отсутствии seed marker. Для размещения используются проверенные файлы баз и исходный owner allowlist, не seed payload.

Подготовленный `deploy/compose.legacy.yaml` является отдельным проектом, без опубликованных портов. По умолчанию профиль migration не запускается. Дополнительно запуск отказывает без явного `LEGACY_CUTOVER_CONFIRMED=true`, токена и обеих существующих баз; он не создаёт незаметно пустую новую базу. Сам шаблон не доказывает выключение старого Telegram receiver — это отдельная проверка оператора.

На VPS Compose проверен с отдельными синтетическими каталогами и network_mode none: `config --quiet` прошёл, четыре попытки запуска без cutover flag, токена, allowlist или файлов БД отказали с соответствующими безопасными кодами. Настоящий токен и базы старого бота в эти проверки не передавались, polling не запускался.

Создать приватные каталоги конфигурации и данных вне checkout. Скопировать `deploy/examples/legacy.env.example` в `bot.env` mode 0600, заполнить исходные значения приватно. Сохранить прежний allowlist; не заменять его пустым значением и не определять владельца по первому посетителю. Параметры `LEGACY_IMAGE`, `LEGACY_CONFIG_DIRECTORY`, `LEGACY_DATA_DIRECTORY` задаются оператором явно. Каталог данных и логи должны быть доступны UID 10001; исходные backup archives остаются неизменными.

Проверка без запуска получателей:

    docker compose -f deploy/compose.legacy.yaml --profile migration config --quiet

Для реального переключения согласовать короткое окно и проверить, что старый процесс остановлен и Telegram webhook/другой poller не остаётся активным. Сделать последнюю согласованную SQLite backup API копию либо подтвердить выбранную архивную точку восстановления. Записать hashes/counts отдельно для заметок, напоминаний и тренировок. Подготовить откат до первого старта. Только после этого приватно включить флаг и запустить профиль migration.

После старта проверить единственный приёмник, команды заметок/напоминаний и тренировок, пользовательские настройки, расписание, журнал ошибок и состояние healthcheck. Устаревшие напоминания могут отправиться сразу после запуска: их список и желаемое поведение нужно согласовать до запуска. Не включать второй экземпляр для проверки. При откате сначала остановить новый процесс, затем возвращать один старый; сохранить изменения, созданные после переключения.

Внешняя зашифрованная копия CRM не заменяет отдельное резервирование SQLite старого бота. Не закрывать Amvera и не удалять архивы до проверки сохранности данных и восстановления.
