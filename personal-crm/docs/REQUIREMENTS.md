# Personal CRM: требования для разработки

Дата передачи: 13 октября 2026 года. Статус: спецификация, а не реализованный продукт.

Этот документ вместе с `OPENAI_API.md` и `ACCEPTANCE.md` переносит требования из интервью и документов CRM_requirements_v0.1.md и CRM_OpenAI_API_addendum_v0.2.md. Это консолидированная редакция, не побайтовая копия. Требования пользователя R отделены от проектных настроек D. Примеры являются синтетическими сценариями испытаний, не поручениями создавать настоящие напоминания. Реальные аккаунты, ключи и личные данные в репозиторий не передаются.

## 1. Цель и границы

Однопользовательская система управления личными обязательствами. Пользователь записывает мысль одной фразой боту или пересылает сообщение из другого чата. Система сохраняет дело, помогает не откладывать его бесконечно и сопровождает до выполнения, отмены или осознанного переноса. Почта автоматически поставляет предложения задач, но не создаёт обязательства без подтверждения.

Telegram нужен для ввода и оперативных действий, адаптивное веб-приложение для обзора, поиска, источников и настроек. У обоих одна база задач. Не строить классическую CRM продаж с клиентскими воронками. Система не узнаёт мысли, которые пользователь не записал; не читает остальные Telegram-чаты. Изменение исходной переписки становится известно только после новой пересылки или команды владельца.

## 3. Изменяемые проектные настройки по умолчанию

| ID | Исходное решение |
|---|---|
| D01 | Ежедневная сводка в 12:00 по часовому поясу профиля. Это настройка, не предположение о времени пробуждения. |
| D02 | Проверить и перенести пояс из старого бота. Если его нет, явно предложить пояс устройства при первом входе. Не подставлять пояс сервера или геолокацию молча. До определения пояса относительные даты не активируют расписание. |
| D03 | Единственный повтор при отсутствии ответа через 4 часа. |
| D04 | Лимит двух сообщений ограничивает дополнительную инициативу системы. Явно назначенные точные напоминания не расходуют лимит; их автоматические повторы расходуют. |
| D05 | Лимит считается по календарной дате профиля; сводка отдельно. Между двумя инициативными сообщениями минимум 4 часа, в том числе вокруг полуночи. |
| D06 | Счётчик переносов учитывает планируемое выполнение, но не перенос уведомления на час и не молчание. |
| D07 | Первый почтовый адаптер: один личный ящик, входящие и отправленные, без спама, корзины и черновиков. Провайдер пока неизвестен. |
| D08 | Первичная обработка последних 7 дней, затем новые данные и изменения уже обработанных цепочек. |
| D09 | Предложения из почты идут в сводку. Возможный срок до следующей сводки допускает отдельное сообщение в пределах лимита. |
| D10 | Внешний календарь не входит в первый релиз. Встречи можно хранить как внутренние события. |
| D11 | Исходящие уведомления только в Telegram. Веб не дублирует их push-сообщениями. |
| D12 | Разбиение создаёт предлагаемый план, не самостоятельные обязательства с выдуманными дедлайнами. |
| D13 | Заметка не становится задачей без признаков действия. Задача без срока сохраняется без обязательного уточнения дедлайна. |
| D14 | Доступ только владельцу, публичная регистрация отключена. |
| D15 | Облачный ИИ и почта не обрабатывают реальные данные до настройки доступа и явного разрешения соответствующих категорий передачи. |
| D16 | Нерелевантные полные письма не хранятся постоянно: временный кэш очищается через 7 дней. Доказательные фрагменты подтверждённых задач сохраняются с задачами. |
| D17 | Ежедневные зашифрованные резервные копии вне сервера, хранение 30 дней. Проверка восстановления перед выпуском и регулярно. При уничтожении сервера возможна потеря до 24 часов данных с такой частотой копий. |

Пустая автоматическая сводка не отправляется. Запрос плана работает в любое время и не расходует инициативный лимит. Ручные ограничения являются верхней границей адаптации. Даты и интервалы задаются конфигурацией, а не зашиваются в промпт модели.

## 4. Данные и состояния

Исходная запись хранит канал, внешний идентификатор, текст, доступные сведения об авторе, время получения, время оригинала, версию и состояние обработки. Она фиксируется до запроса модели. Не сохранять выдуманные метаданные.

Основные типы: задача пользователя; ожидание чужого ответа; внутреннее событие; заметка/идея; предложение; напоминание; журнал изменений. Проект необязателен. Ожидание не становится обязанностью пользователя выполнить чужое обещание. Напоминание проверить ответ не разрешает отправлять сообщения третьему лицу.

Задача бывает активной, в работе, отложенной, выполненной, отменённой. Просрочка вычисляется из срока и состояния, не заменяет собой состояние задачи. Предложение бывает ожидающим, принятым, отклонённым или устаревшим. Молчание не означает принятие. Отклонённое предложение не появляется снова при обработке того же неизменившегося источника.

Хранить отдельно исходный дедлайн, текущий согласованный дедлайн, план выполнения, дату возвращения, расписания уведомлений и правило повторения. Различать дату без времени и точный момент, хранить исходную формулировку и часовой пояс. Не превращать дату без времени в якобы сказанные пользователем 23:59. Неоднозначная граница «до пятницы» не получает выдуманную точность.

«Напомни завтра» меняет напоминание, не дедлайн. «Сделаю завтра» при однозначной задаче задаёт план выполнения. «Перенеси на завтра» требует уточнения только если по контексту нельзя определить переносимый параметр. Исходный срок сохраняется при последующем согласованном изменении.

История содержит инициатора, основание, предыдущее и новое значения, связанную команду/подтверждение, версию объекта. Одновременные изменения веба и Telegram проверяют версию. Запоздалое подтверждение не должно затирать более новую правку.

## 5. Обработка ввода и полномочия

Порядок: проверить владельца и канал; надёжно сохранить источник с защитой от технических повторов; определить границу доверия; распознать действие/исполнителя/срок/связь с делами; проверить структуру, смысл, даты и разрешение; записать задачу, предложение или уточнение; транзакционно записать историю и задания; только затем ответить о результате.

Если сохранён только источник, нельзя писать «задача создана». При сбое ИИ допустимо «Сообщение сохранено. Разбор пока не завершён». При сбое БД нельзя подтверждать даже сохранение. Уточнение по одной записи не блокирует ввод новых дел. «Да» связывается с конкретным предложением и версией; при нескольких кандидатах бот уточняет, а не угадывает.

Не заставлять выбирать категорию, проект и приоритет. Уточнять только существенно недостающее: о каком деле речь, исполнитель, неоднозначная дата, вид изменения. Исправление уже обработанного сообщения создаёт новую версию источника; изменение дела предлагается, если нет явной однозначной команды применить правку. Отмена последнего ошибочного изменения должна учитывать более поздние изменения из других интерфейсов.

Пересланные и почтовые тексты не обладают полномочиями владельца. «Удали все задачи» внутри письма не является командой. Модель не имеет прямого произвольного доступа к БД, ящику или отправке сообщений.

Очевидная пересылка может создать новое дело с источником. Новая задача из почты всегда только предложение. Предлагаемый ИИ перенос срока, напоминания или состояния требует подтверждения. Письмо, предположительно подтверждающее выполнение, только предлагает закрыть задачу. Однозначное «выполнил» от владельца выполняется сразу.

Разбиение сложной задачи автоматически создаёт черновые шаги без самостоятельных уведомлений. Предположения обозначаются. Превращение плана в активные подзадачи требует одного понятного подтверждения всего плана. Сроки шагам не назначаются без основания/подтверждения. Изменения ранее существующего плана по инициативе ИИ требуют подтверждения.

## 6. Telegram и относительные даты

Бот принимает обычный текст и пересылки, отвечает коротко на русском. Базовые сценарии создания, поиска, переноса и закрытия не требуют кнопок. Не включать клиентский доступ ко всем чатам пользователя.

Дата «завтра» в старой пересылке не вычисляется от момента пересылки автоматически: учитывается дата оригинала. Если значимые контекст или пояс неизвестны, задать уточнение. Telegram может скрыть автора; полная ссылка на исходный личный чат не гарантируется. Сохранить реально доступные текст и метаданные, не выдумывать автора, получателя и ссылку. Контекст разрешено дополнять следующим связанным сообщением или ответом на пересылку.

Технический повтор одного Update не создаёт новую задачу. Новая ручная пересылка похожего текста отличается от технического повтора: смысловое сходство само по себе не разрешает объединять или удалять обязательства.

## 7. Сопровождение задач

Сводка: до трёх главных дел, ближайшие сроки и просрочки, одна-две давно не обсуждавшиеся задачи без срока, ожидания, предложения из почты, важные ошибки синхронизации. Одна компактная отправка с количеством остальных дел и переходом к полному списку; единственный срочный дедлайн не скрывается ради компактности. Полный обзор по запросу и в вебе.

Объяснимый стартовый порядок: явно выбранный пользователем фокус, ближайшие внешние сроки, просрочки с возможным действием, подтверждённый план на сегодня, давно не обсуждавшиеся дела. Ранжирование предлагает, но не изменяет обязательства. Задачи без срока возвращаются с учётом времени последнего показа/обсуждения, чтобы маленькая группа не вытесняла остальные. Выполненные, отменённые и отложенные до будущей даты исключаются из обычных напоминаний.

Задача с дедлайном присутствует в ежедневном обзоре. Дополнительно предложить более раннее выполнение и небольшой стартовый шаг, не спрашивать одинаковое ежедневно. Принятие нового плана требует подтверждения.

Перед повтором через 4 часа проверить актуальность задачи, напоминания, ответов и настроек. Ответ API об отправке не доказывает прочтение. Постороннее сообщение боту не следует автоматически считать ответом на все напоминания. Пользовательское выполнение/отмена/согласованный перенос отменяет устаревший повтор. Один повтор расходует инициативный лимит.

После третьего переноса выполнения один раз предложить разбор препятствия и варианты решения. Не делать это ежедневно. Новый разбор допускается после нового значимого переноса/ответа, не просто по таймеру.

О просрочке сообщить один раз. При исчерпанном лимите явно включить факт в ближайшую сводку; далее задача остаётся в обзоре без одинакового отдельного сообщения каждый день. Новый план не стирает старую просрочку. Срочное почтовое предложение может заменить ещё не отправленную менее срочную инициативу, но не превышает лимит молча.

У регулярного дела различать правило повторения и отдельное выполнение: «сделал» закрывает текущий экземпляр, не весь ряд. Отмена регулярности требует явной команды. При неуказанном времени предложить настройку по умолчанию и не выдавать её за сообщённое пользователем время.

## 8. Почта

Провайдер и адрес неизвестны. Создать сменный адаптер для подключения, чтения сообщений/цепочек, получения изменений, проверки доступа и отключения. Наличие Gmail в инструментах чата не является выбором почтового сервиса продукта. Реальный первый адаптер подключается к выбранному при настройке ящику, не искать его в пользовательском аккаунте автоматически.

Минимальные права только чтения, без отправки, удаления, изменения писем. Входящие и отправленные используются для просьб и собственных обещаний. Найденные задачи, сроки, отмены, ответы формируют предложения с доказательным фрагментом и датой. Отправленное письмо не доказывает выполнения любого упомянутого действия.

Сверка изменений стартово каждые 5 минут с квотами, ограниченными повторами и задержкой после ошибок. Контрольную точку продвигать после надёжного сохранения. Не перечитывать и не анализировать весь ящик каждый цикл. Предусмотреть восстановление после устаревшей контрольной точки. Даже при последующем добавлении push нужна периодическая сверка.

HTML отображать безопасно. Внешние изображения и ссылки автоматически не загружать. Вложения, сканы и голос в первую версию анализа не входят. Система должна явно сообщать, что недоступное вложение не анализировалось.

## 9. Веб-приложение

Русскоязычный адаптивный интерфейс для телефона и компьютера: Сегодня; Все дела с поиском/фильтрами; Входящие с предложениями/уточнениями; Проекты; Настройки. Фильтры по состоянию, сроку, проекту, источнику и типу. Карточка содержит действие, состояние, точность сроков, следующий шаг, источник, историю.

В Настройках видны пояс, сводка, лимиты, интеграции, доступ, ИИ, экспорт, состояние копий. Основной экран не подменять диаграммами. Веб-кнопки допустимы; Telegram не должен зависеть от них. Явная правка через веб считается действием пользователя с проверкой версии записи.

## 10. Архитектура и миграция

Одно модульное Python-приложение: FastAPI; PostgreSQL для источников, задач, предложений, истории и постоянной очереди; приёмник Telegram; отдельный фоновый процесс; React/TypeScript для веба; отдельный Docker Compose. Уведомления и задачи меняются одной транзакцией. Очередь использует блокировки, ограниченное время владения заданием и восстановление после остановки; SKIP LOCKED сам по себе не решает доставку. Начальная архитектура без Redis, векторной БД и микросервисов. Версии зависимостей фиксируются после проверки совместимости.

ИИ сменный, формирует предложения. База и детерминированный код отвечают за время, полномочия, лимиты, сохранение, поиск и доставку. Без ИИ сводка формируется шаблоном, существующие напоминания продолжаются. Не обещать свободное понимание любого текста при отключённой модели.

Новый код создавать внутри `personal-crm/`, существующие `bot/`, `main.py`, конфигурацию развёртывания и тренировки не менять в начальной задаче. Сначала прочитать реальные модули, схемы, расписание и тесты, а не полагаться на README. Составить карту повторного использования и регрессионных рисков.

Будущая миграция отдельно: тесты существующего поведения; пробный импорт копии SQLite в PostgreSQL; сверка записей, сроков, регулярности, неперенесённых полей; резервная копия; остановка старой доставки до новой; один приёмник Telegram и один владелец расписания; проверка и план отката. Тренировки остаются отдельно, их данные не передавать ИИ. Проверить конфликты команд тренировок и свободного ввода задач. Производственная миграция и переключение сейчас не разрешены.

## 11. Надёжность и безопасность

Подтверждённые записи переживают рестарт. После простоя не отправлять всю накопившуюся очередь подряд: проверить актуальность, подготовить краткое сообщение о пропущенном и сохранить подробный журнал. Позднее точное напоминание обозначать как опоздавшее. Не обещать безусловную доставку ровно один раз: провайдер мог принять сообщение до сетевого обрыва. Такое состояние хранить как неопределённое. Допускается один ограниченный повтор с внутренним идентификатором и пометкой о возможном повторе, в пределах лимита; бесконечные повторы запрещены.

Telegram хранит неполученные обновления не дольше 24 часов: долговременный простой до приёма не покрывается гарантией полного восстановления. Нужны мониторинг и честное сообщение о возможном пробеле.

Владелец задаётся доверенной конфигурацией, не первым посетителем. При отсутствующем владельце доступ закрыт. Проверять принадлежность каждого объекта и канала, веб-аутентификацию, защищённые сессии, HTTPS при публикации. Реальные ключи, тексты задач/писем и дампы отсутствуют в репозитории и прикладных логах. Для диагностики только идентификаторы и категории ошибок.

Перед облачным ИИ показать категории передаваемых данных. Передавать только необходимый фрагмент, не всю историю и ящик. Рабочие данные/корпоративную почту без отдельного разрешения не подключать.

Экспорт включает дела, сроки, заметки, источники в пределах хранения, предложения, историю. Удаление должно иметь политику очистки основной базы и истечения копий; при восстановлении повторно применять зарегистрированные удаления, чтобы незаметно не возвращать удалённое.

Показывать последнюю успешную синхронизацию, последнюю ошибку, состояние фонового процесса, очередь и возраст копии. «Нет новых дел» не равно «не удалось проверить». Полную недоступность сервера проверяет внешний мониторинг при реальном развёртывании; сервис и расходы неизвестны, подключение не выполнено.

## 12. Порядок выпуска и ограничения

Порядок: аудит текущего проекта; надёжное ядро и очередь; свободный ввод Telegram; сопровождение и симуляция нескольких недель; чтение почты и предложения; веб поверх той же базы; пробная миграция, восстановление и пилот. Конкретная первая задача находится в `../CODEX_TASK.md`.

За пределами первого релиза: все чаты Telegram, внешний календарь, отправка сообщений другим людям, ответы на почту, голос, вложения, нативные мобильные приложения, многопользовательский сервис, воронки продаж, автономные изменения обязательств.

До реального запуска остаются параметры: почтовый сервис/ящик, проверенный пояс, сервер, адрес веба, модель, секреты, допустимые расходы. Неизвестные параметры не останавливают разработку на fake-адаптерах и не подменяются выдуманными фактами. Пользователь поручил продолжать без новых продуктовых вопросов.
